# ADR-001: Обоснование решения для пакетной обработки

**Статус:** ⚠️ На рассмотрении  
**Участники:** Владелец продукта; архитектор решения  
**Дата:** 2026-11-01

## Функциональные требования

1. Выполнять ETL средствами Spring Batch: читать товары из `product-data.csv`, обогащать данными программы лояльности из `loyality_data` и сохранять в `products` PostgreSQL.
2. Принимать CSV через ERP, сохранять в GCS и обрабатывать асинхронно.
3. Проверять формат CSV до изменения данных; сообщать об ошибках для исправления и повторной загрузки.
4. Обогащать отчёты справочными данными и сохранять результат в БД номенклатуры.
5. Повторять обработку при восстановимых ошибках и возобновлять с сохранённого прогресса без повторной загрузки файла и дублирования изменений.
6. Показывать статус и прогресс обработки; уведомлять пользователя об успешном завершении или ошибке.
7. Формировать отложенную отчётность ночью, независимо от обработки загруженных отчётов.
8. Централизованно собирать логи и метрики; оповещать операторов о сбоях и задержках.

## Решение

Выбрать Spring Batch для пакетного ETL с асинхронным запуском и интеграцией с мониторингом. Этот вариант сочетает восстановление обработки внутри отчёта, совместимость с Java и меньший объём собственной разработки. Опыт инжиниринг-лида дополнительно снижает затраты на освоение.

Развернуть обработку отдельным Java-приложением рядом с монолитом. ERP сохраняет CSV в GCS, регистрирует задание и возвращает идентификатор отслеживания. Диспетчер запускает принятые задания через `JobLauncher` с ограничением параллельной нагрузки на БД. Spring Batch выполняет валидацию, обогащение и пакетную запись; `JobRepository` в PostgreSQL хранит состояние и прогресс выполнения.

Приём файлов, передача заданий, статусы в ERP, уведомления и защита от повторного применения изменений обеспечиваются прикладной логикой и интеграциями. Ночная отчётность выполняется отдельным заданием по расписанию.

POC демонстрирует ETL товаров в локальном Java-приложении с PostgreSQL и Docker Compose. Интеграции ERP/GCS и остальные функции целевой системы не объявляются реализованными в POC.

| Требование                            | Реализация в выбранном решении                                                                                                                                                                                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. ETL товаров                        | `FlatFileItemReader` читает `product-data.csv`; `ItemProcessor` обогащает товары данными из `loyality_data`; `JdbcBatchItemWriter` сохраняет результат в `products` PostgreSQL.                                                                                    |
| 2. Приём и асинхронная обработка      | Прикладной компонент сохраняет CSV в GCS и регистрирует ожидающее задание. После подтверждения приёма диспетчер запускает обработку независимо от запроса пользователя; прерванная передача восстанавливается.                                                     |
| 3. Валидация CSV                      | Отдельный шаг проверяет формат всего файла до записи результатов. Ошибка останавливает задание; ERP получает сообщение и сведения для исправления и повторной загрузки.                                                                                            |
| 4. Обогащение и сохранение отчётов    | Обработчик получает справочные данные для очередной порции записей; компонент записи сохраняет обогащённые данные в БД номенклатуры пакетными операциями.                                                                                                          |
| 5. Повторные попытки и восстановление | Настроенные повторные попытки обрабатывают восстановимые ошибки. Перезапуск использует сохранённый файл, идентичность задания и подтверждённый прогресс; незавершённая порция откатывается. Прикладная логика записи предотвращает повторное применение изменений. |
| 6. Статус, прогресс и уведомления     | Сервис статусов связывает идентификатор отчёта с состоянием приёма и данными выполнения Spring Batch. ERP показывает статус и подтверждённый прогресс; обработчики завершения отправляют уведомления об успехе или окончательной ошибке.                           |
| 7. Ночная отчётность                  | Планировщик запускает отдельное задание формирования отчётности ночью. Импорт складских данных запускается после приёма файла независимо от расписания отчётности.                                                                                                 |
| 8. Логи, метрики и оповещения         | Логи и метрики обработки передаются в централизованный мониторинг с идентификатором отчёта. Контролируются ожидание, длительность, прогресс, ошибки и нагрузка; правила оповещения сообщают операторам о сбоях и задержках.                                        |

### Ограничения

| Ограничение                                                 | Значение для выбранного решения                                                                                                                                               |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Масштабирование импорта связано с нагрузкой ERP на общую БД | Добавление обработчиков не обеспечивает независимого роста пропускной способности импорта. Его параллелизм ограничен ресурсами БД, доступными без ухудшения отзывчивости ERP. |

**Контрмеры**

1. **Отдельная БД чтения для ETL.** Сервисы ERP поддерживают в ней актуальную проекцию справочных данных; ETL получает доступ только на чтение. Это переносит чтение для обогащения с операционной БД ERP. Необходимо контролировать задержку и сбои синхронизации. Для разделения нагрузки записи результат ETL также должен сохраняться в отдельно обеспеченной ресурсами БД PostgreSQL; применимость этого шага зависит от роли `products` как операционных данных ERP или независимого набора для чтения.

2. **Передача изменений от ETL в ERP через Kafka.** ETL сохраняет результат в собственной БД PostgreSQL и надёжно публикует изменения в Kafka. Потребитель ERP применяет их к операционной БД с контролируемой скоростью, сглаживая пики нагрузки. Предусмотреть доставку без потери сохранённых результатов и защиту ERP от повторного применения изменений. Различать завершение ETL и подтверждённое применение данных в ERP. При длительном превышении скорости поступления над скоростью применения изменений очередь растёт.

### Риски

Здесь рассматриваются внешние для решения риски.

| Риск                                                                  | Основание в кейсе                                                                                           | Последствие для решения                                                                                                            |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Пиковая нагрузка превысит прогноз                                     | Сезонные всплески, рекламная кампания и привлечение новых партнёров; 100–150 загрузок — ожидаемая нагрузка. | Возможны рост очередей и задержки обновления остатков; потребуется увеличение доступной мощности обработки и применения изменений. |
| Новые источники окажутся несовместимы с текущими входными контрактами | Запланированы расширение номенклатуры и интеграция с дополнительными источниками данных.                    | Потребуются адаптация входных контрактов и расширение обработки; возрастёт объём интеграционных работ.                             |
| Ошибки в отчётах складов задержат обновление данных                   | Кейс предусматривает ошибки формата, исправление отчёта пользователем и повторную загрузку.                 | Актуализация остатков зависит от исправления внешних данных; автоматические повторы обработки эту зависимость не устраняют.        |

## Альтернативы

Сопоставление по пяти критериям приведено в [alternative.md](./alternative.md).

| Альтернатива | Возможности | Причина отклонения |
|---|---|---|
| Apache Airflow с ETL-задачами | Параллельная обработка, восстановление завершённых этапов, централизованный контроль и координация между сервисами. | Не выбран для текущего ETL: требует освоения и сопровождения отдельной платформы, а также доработок восстановления внутри отчёта. Возможны задержки запуска после загрузки. Остаётся вариантом для координации расширяющихся пайплайнов. |
| Собственное Java ETL-приложение с Quartz | Совместимость с Java, параллельный запуск, расписания и повторные попытки без отдельной платформы исполнения. | Требует больше собственной разработки для восстановления отчётов, наблюдаемости и координации обработки, чем выбранный Spring Batch. |
