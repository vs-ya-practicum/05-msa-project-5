## Подготовка и запуск

Нужны Docker с Docker Compose и Bash для сценариев демонстрации. Java 17 и Gradle используются внутри сборочного контейнера. Команды ниже выполняются из `realization/task-5/results/etl/`.

При первом запуске создать локальный `.env`, сохранив существующий файл, если он уже есть:

```bash
test -f .env || cp .env.example .env
```

Проверить значения подключения. В выполненной демонстрации `POSTGRESDB_LOCAL_PORT=5433`, поскольку порт хоста `5432` был занят. Внутри Docker PostgreSQL использует `5432`.

```bash
docker compose config --quiet
docker compose build
docker compose up -d
```

Gradle и зависимости кэшируются между сборками. Дашборд, источник данных и правила Grafana загружаются из файлов provisioning. Приложение запускает задание один раз и остаётся доступным для сбора итоговых метрик.

| Сервис                      | Адрес                                                                         |
| --------------------------- | ----------------------------------------------------------------------------- |
| Grafana: дашборд            | [localhost:3000/d/batch-processing](http://localhost:3000/d/batch-processing) |
| Grafana: правила оповещения | [localhost:3000/alerting/list](http://localhost:3000/alerting/list)           |
| Prometheus                  | [localhost:9090](http://localhost:9090)                                       |
| Elasticsearch               | [localhost:9200](http://localhost:9200)                                       |
| Kibana                      | [localhost:5601](http://localhost:5601)                                       |

Prometheus обращается к JMX Exporter внутри сети Compose по адресу `app:9404/metrics` каждые 5 секунд. Дашборд обновляется каждые 5 секунд, правила оповещения проверяются каждые 10 секунд.

## Повторяемые сценарии

После запуска стека использовать [demo.sh](./etl/demo.sh). При каждом вызове скрипт создаёт новую БД в работающем PostgreSQL, инициализирует таблицы и пересоздаёт только контейнер приложения. Предыдущие БД сохраняются; мониторинг и сбор логов продолжают работать. Образ приложения повторно не собирается.

| Команда                | Условие                                         | Ожидаемый результат                                                                                                                                                    |
| ---------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bash demo.sh normal`  | Ошибка и задержка отключены                     | Одно успешное выполнение, пять сохранённых записей, прогресс 100%, оба правила в состоянии Normal.                                                                     |
| `bash demo.sh failure` | Ошибка на SKU `50001`, четвёртой входной записи | Одно неуспешное выполнение, три сохранённые записи, прогресс 60%; `BatchJobFailed` переходит в Firing.                                                                 |
| `bash demo.sh slow`    | Задержка 20 секунд на запись                    | Около 100 секунд обработки; `BatchJobTooLong` переходит в Firing после превышения 60 секунд и возвращается в Normal после завершения. Итог — пять сохранённых записей. |

Запускать сценарии последовательно, дожидаясь результата текущего. Скрипт сбрасывает оба параметра перед выбором сценария. Для возвращения к обычному режиму после демонстрации выполнить `bash demo.sh normal`.

Оповещение о финальном сбое действует пять минут после ошибки. Истечение окна возвращает правило в Normal и не означает восстановление неуспешного задания. Длительное выполнение не прерывается оповещением.

## Просмотр логов в Kibana

1. Открыть **Stack Management → Saved Objects → Import** и импортировать [batch-processing.ndjson](./etl/kibana/batch-processing.ndjson). Оставить **Create new copies** выключенным, чтобы сохранить идентификатор `batch-processing-logs`.
2. Открыть **Discover**, выбрать `batch-processing-*` и диапазон времени, включающий нужный запуск. Для вчерашних запусков увеличить диапазон, например до **Last 7 days**.
3. Найти события задания запросом `etl.job_name : "importProductJob"`.
4. Для успешного завершения проверить `etl.event : "job_finished"`: статус `COMPLETED`, `read_count=5`, `write_count=5` и идентификатор выполнения.
5. После сценария `failure` найти `etl.stack_trace : "Demonstration failure requested for SKU 50001"`. Запись **Step execution failed** содержит стек ошибки, `etl.job_execution_id` и `etl.step_execution_id`.

JSON разбирается один раз в Logstash. Поля приложения находятся под `etl`, а верхнеуровневый `@timestamp` содержит время события приложения.

## Подтверждение результата

В локальной проверке подтверждены успешная обработка, сбор всех восьми метрик, поиск структурированных логов с идентификаторами выполнения, оба сценария ошибок/задержки, срабатывание и возврат правил в Normal, повторный обычный запуск через общий скрипт.

## Границы демонстрации

POC обрабатывает один CSV из пяти записей, одно задание за раз. Загрузка через ERP/GCS, очереди, Kafka и остальные целевые интеграции не реализованы в этом POC. Показатели для отчёта на 2 000 строк и 100–150 параллельных загрузок здесь не подтверждаются.

Счётчики приложения сбрасываются при пересоздании его контейнера; итоговые значения текущего запуска доступны, пока процесс работает. Prometheus сохраняет уже собранные временные ряды. Идентификаторы выполнения следует рассматривать вместе со временем запуска: демонстрационные БД независимы.

Срабатывание и завершение оповещений демонстрируются в интерфейсе Grafana. Внешний канал доставки уведомлений не выбран и не настроен.
