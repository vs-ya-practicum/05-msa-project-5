## Функциональные требования

1. Централизованно собирать логи операций Spring Batch-приложения.
2. Предоставлять возможность просматривать и искать собранные логи для установления причин ошибок обработки данных.
3. Обеспечивать связь записей логов с конкретным выполнением задания и шага ETL, чтобы проследить чтение CSV, обогащение данных и сохранение результата.

## Нефункциональные требования

1. Обеспечивать локальное развёртывание решения средствами Docker Compose с возможностью последующего применения в облачной инфраструктуре.
2. Обеспечивать возможность подключения новых Java-сервисов к централизованному сбору логов при постепенном выделении функциональности из монолита.
3. Учитывать затраты на логирование при обеспечении целевых показателей системы: 100–150 параллельных загрузок и среднего времени обработки отчёта на 2 000 строк не более 30 секунд.

## Решение

### Способ отправки логов и его обоснование

Выбрать централизованное логирование на основе ELK с доставкой логов через Filebeat. Spring Batch-приложение записывает структурированные JSON-логи в файлы; Filebeat собирает их и передаёт в Logstash. Logstash разбирает и нормализует записи перед отправкой в Elasticsearch. Elasticsearch хранит логи и обеспечивает поиск, Kibana используется для их просмотра и анализа.

Путь доставки логов: `Spring Batch → файлы логов приложения → Filebeat → Logstash → Elasticsearch → Kibana`.

Выбор обосновывается применимостью этого стека к заданию 5 и проблемам TradeWareб и способом доставки логов приложения.

| Основание                                                                          | Обоснование выбранного решения                                                                                                                                    |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| В TradeWare есть файловые логи, но трудно установить причины ошибок                | Централизованный сбор в Elasticsearch и просмотр в Kibana дают единое место для поиска и анализа ошибок пакетной обработки.                                       |
| Требуется централизованный сбор логов и постепенное выделение сервисов из монолита | Общий контур логирования позволяет собирать записи Spring Batch-приложения и впоследствии подключать дополнительные сервисы.                                      |
| Необходимо организовать доставку логов приложения                                  | Приложение сохраняет файловое логирование, а сбор и передачу выполняет Filebeat. Приложению не требуется самостоятельно отправлять каждую запись в Elasticsearch. |
| Требуется обработка записей перед индексированием                                  | Logstash служит общей точкой разбора и нормализации логов Spring Batch-приложения и подключаемых в дальнейшем сервисов.                                           |

Для ETL из задания 4 записывать начало, завершение и ошибки выполнения заданий и шагов. Включать временную метку, уровень логирования, имя приложения, идентификаторы выполнения задания и шага, счётчики обработки, длительность и сведения об ошибке, когда они применимы. Эти данные позволяют связать сбой с конкретным выполнением чтения `product-data.csv`, обогащения данными из `loyality_data` и записи в `products`.

### Способ конфигурации оповещений и его обоснование

Выбрать Grafana-managed alerting с файловой конфигурацией через provisioning Grafana. Правила используют метрики Prometheus. Файлы правил и политик уведомлений хранить в репозитории вместе с конфигурацией Docker Compose и подключать при развёртывании.

| Решение | Обоснование |
| --- | --- |
| Вычисление правил в Grafana | Grafana уже используется для дашборда. Правила и их состояния доступны в том же интерфейсе, что и метрики; для локального POC не требуется добавлять Alertmanager. |
| Файловая конфигурация через provisioning | Позволяет повторять локальное развёртывание с одинаковыми правилами, просматривать изменения конфигурации в Git и переносить её вместе с проектом. |

Конкретные правила, пороги, интервалы и поведение оповещений описаны в [документе метрик](./metrics.ru.md#оповещения).
