# ADR-001: Выбор решения для пакетной обработки

**Статус:** ⚠️ На рассмотрении  
**Участники:** Владелец продукта; архитектор решения  
**Дата:** 2026-10-31

## Функциональные требования

- Гибко задавать пайплайн обработки данных, зависимости между шагами, ветвления и условное выполнение.
- Поддерживать интеграцию с внешними API, BigQuery, Redshift, Kafka и Spark, используя готовые модули там, где они доступны.
- Поддерживать запуск по событиям, повторные попытки и переход к резервной логике при сбоях.
- Предоставлять встроенный мониторинг выполнения и возможность отправлять email-уведомления об успешном и неуспешном завершении пайплайна.
- В локальном POC продемонстрировать чтение из базы данных или файловой системы, анализ данных, условное ветвление, retry-политику и email-уведомления.

При выборе также учитываются нефункциональные требования: обработка около одного миллиона записей за запуск, возможность локального развёртывания и последующего применения в облачной инфраструктуре. Размер записей, сложность преобразований и соединений, доступные CPU и память, а также допустимое время выполнения не определены.

## Решение

Предлагается выбрать **Apache Airflow в качестве оркестратора пакетной обработки**, а для первоначального POC использовать **Python/SQL-задачи как предварительный вариант реализации обработки**. Выбор оркестратора не подтверждает достаточность вычислительных ресурсов или производительность задач для ожидаемого объёма данных.

Airflow выбран по совокупности требований: готовые интеграционные модули, управление зависимостями и ветвлениями, retry-механизмы, встроенная видимость выполнения и поддержка уведомлений позволяют реализовать POC без дополнительного фреймворка обработки.

| Требование          | Реализация в выбранном решении                                                                                                                                                                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Внешние API         | HTTP provider предоставляет операторы запросов и сенсоры проверки ответа. Аутентификация, пагинация и обработка ответа конкретного API требуют настройки или кода.                                                                                                      |
| BigQuery            | Google provider предоставляет операторы запросов, загрузки и проверки данных. Требуются подключение и SQL или параметры операций.                                                                                                                                       |
| Redshift            | Amazon provider поддерживает SQL и Redshift Data API. Требуются учётные данные, SQL и выбор способа загрузки.                                                                                                                                                           |
| Kafka               | Kafka provider предоставляет компоненты интеграции. Границы чтения и связь событий с пакетными запусками необходимо определить.                                                                                                                                         |
| Spark               | Spark provider предоставляет, в частности, `SparkSubmitOperator`. Для выполнения необходимы среда Spark и приложение обработки. Наличие интеграции не означает обязательного использования Spark в POC.                                                                 |
| Ветвления и условия | Операторы ветвления выбирают путь выполнения, trigger rules определяют условия запуска последующих задач. Бизнес-условия задаются в пайплайне.                                                                                                                          |
| Запуск по событиям  | Для этого механизма предусматривается Airflow 3: assets, watchers и совместимые event triggers. Требуются настройка источника событий и проверка совместимости используемых providers.                                                                                  |
| Fallback-логика     | Trigger rules позволяют запускать резервные задачи после сбоя. Сами действия восстановления необходимо реализовать.                                                                                                                                                     |
| Retry               | Для задач настраиваются число попыток, задержка и экспоненциальное увеличение задержки. Повторяемые операции должны допускать безопасное повторное выполнение.                                                                                                          |
| Мониторинг и email  | Встроенный UI показывает состояния выполнения и логи задач. SMTP notifier и callbacks настраиваются для успешного и неуспешного завершения DAG; необходимы SMTP-подключение и получатели. Более широкий мониторинг метрик и алертинг требуют дополнительной интеграции. |

**Развёртывание:** локальный POC разворачивается с помощью Docker Compose. Для облачной среды предлагается Kubernetes с официальным Helm chart Airflow и отдельной настройкой хранилища метаданных, секретов, логов и ресурсов задач. Локальная конфигурация POC не считается готовой облачной конфигурацией. Конкретный облачный провайдер не выбран.

**Обработка ожидаемого объёма:** обоснование Python/SQL-задач должно описывать чтение, объединение и обработку около миллиона записей в пределах доступных ресурсов, например ограниченными пакетами и/или средствами базы данных. Достаточность этого подхода пока не установлена. Необходимость Spark, распределённой обработки или отдельного Spring Batch job также не установлена имеющимися данными; выбор уточняется с учётом характеристик нагрузки.

### Требуемые кастомне доработки

- Реализовать DAG и Python/SQL-задачи чтения, объединения, анализа и формирования результата; задать зависимости, условия ветвления и параметры запусков.
- Настроить подключения и учётные данные для используемых источников и внешних систем. Реализовать специфичные для API аутентификацию, пагинацию и обработку ответов там, где готовой конфигурации недостаточно.
- Определить границы пакетного чтения из Kafka и правила запуска по событиям; настроить соответствующие providers и triggers при реализации этих интеграций.
- Реализовать резервные действия после сбоя и безопасное повторное выполнение операций; настроить retry-политику и условия перехода к fallback-задачам.
- Настроить SMTP provider, подключение, получателей и callbacks успешного и неуспешного завершения DAG. При необходимости мониторинга метрик дополнительно настроить их сбор и алертинг.
- Подготовить Docker Compose для локального POC и демонстрацию чтения данных, ветвления, retry и email-уведомлений. Для облачного развёртывания отдельно подготовить конфигурацию Kubernetes и Helm, хранения метаданных, секретов, логов и ресурсов задач.
- Уточнить характеристики нагрузки и обосновать способ обработки около миллиона записей за запуск: размер пакетов, использование SQL, потребление ресурсов и ожидаемое время выполнения. По результатам определить достаточность Python/SQL или необходимость другого механизма обработки.

#### Требования

- Обработка должна учитывать доступные CPU и память: размер пакетов и способ выполнения соединений должны обеспечивать выполнение в пределах выделенных ресурсов. Допустимое время выполнения необходимо определить до оценки производительности.
- Повторное выполнение задачи после частичной записи результата не должно создавать дубликаты или повторно применять изменения.
- Для Kafka должны быть определены границы чтения каждого пакета и правила соответствия событий запускам, исключающие непреднамеренную повторную обработку.
- Успешность пайплайна должна определяться получением требуемого результата обработки. Успешное выполнение fallback-задачи само по себе не должно означать успешное завершение бизнес-обработки.
- Настройка SMTP и callbacks должна обеспечивать отправку уведомлений для успешного и неуспешного завершения DAG.
- Выбранные версии Airflow и providers должны быть совместимы с используемыми интеграциями и event triggers. Конфигурация облачного развёртывания должна учитывать отличия от локального POC.
- Для каждого резервного пути должны быть определены восстанавливаемый результат, допустимое состояние после сбоя и необходимые компенсирующие действия.
- Для задач, которым требуется продолжение обработки с конкретной записи или пакета, необходимо реализовать сохранение прогресса и правила возобновления в самой обработке либо выбрать механизм обработки с такой поддержкой.
- Мониторинг должен различать состояние выполнения DAG и корректность полученного результата. Проверки результата и необходимые метрики обработки должны быть определены в задачах; при использовании внешней системы мониторинга должны быть настроены сбор метрик и правила оповещения.
- Выводы локального POC должны отдельно указывать продемонстрированные функции и неподтверждённые характеристики: производительность на целевом объёме и готовность облачного развёртывания нельзя считать доказанными демонстрацией простого пайплайна.

### Ограничения

Ограничения ниже описывают границы возможностей выбранного состава решения, сохраняющиеся при корректной реализации.

| Ограничение | Значение для выбранного решения |
|---|---|
| Оркестрация и обработка масштабируются на разных уровнях. | Airflow управляет запуском задач, но не превращает Python/SQL-обработку внутри отдельной задачи в распределённое вычисление. Распределённая обработка потребует отдельного механизма, например Spark, и расширит выбранный состав решения. |
| Единица восстановления средствами Airflow — задача, а не запись или чанк данных. | Повторная попытка Airflow не предоставляет встроенного продолжения Python/SQL-обработки с последней успешно обработанной записи. Такое восстановление остаётся за границей механизма retry оркестратора даже при корректно настроенной политике повторов. |
| Встроенная наблюдаемость Airflow относится к выполнению пайплайна. | Состояния DAG и задач, а также их логи не устанавливают полноту и бизнес-корректность отчёта. Без явно заданных проверок успешное выполнение не является подтверждением качества результата; эти проверки относятся к прикладной обработке. |

### Риски

Оценка ниже относится к неопределённостям, способным изменить обоснованность архитектурного выбора. Основания взяты из настоящего ADR; последствия являются выводами, вероятность и стоимость которых пока не установлены.

| Риск | Основание в текущем решении | Последствие для архитектурного выбора |
|---|---|---|
| Предварительно выбранный механизм обработки окажется недостаточным для реальной нагрузки. | Известно количество записей, но не определены их размер, сложность преобразований и соединений, ресурсы и допустимое время выполнения. Python/SQL выбран предварительно. | Может потребоваться Spark или отдельный фреймворк обработки. Тогда изменятся состав решения, объём разработки и стоимость эксплуатации; простота первоначального POC не подтвердит простоту целевой системы. Выбор Airflow как оркестратора при этом может сохраниться. |
| Реальный объём кастомной разработки окажется существенно больше ожидаемого от использования готовых providers. | Конкретные API, правила объединения данных, границы чтения Kafka и действия бизнес-восстановления пока не описаны. Наличие модуля интеграции не устанавливает покрытие этих сценариев. | Преимущество Airflow по сокращению разработки может оказаться слабее принятого при сравнении альтернатив; сроки и трудоёмкость решения могут увеличиться даже при корректном использовании готовых модулей. |
| Выбранный способ облачного развёртывания окажется экономически или организационно неприемлемым. | Предлагается Kubernetes, но облачный провайдер не выбран, бюджет и условия эксплуатации не установлены. | Стоимость и доступность эксплуатации могут потребовать другого способа размещения, в том числе пересмотра самостоятельно управляемого Airflow. Работоспособность локального POC не разрешает эту неопределённость. |

## Альтернативы

| Альтернатива                          | Возможности                                                                                                                                                                                                                                                                                                                                | Причина отклонения для первоначального POC                                                                                                                                                                                                                                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spring Batch + Spring Cloud Data Flow | Spring Batch предоставляет обработку чанками, retry и механизмы перезапуска; SCDF — централизованную оркестрацию, историю запусков и UI. Условия задаются переходами по статусам, `JobExecutionDecider` и Composed Task Runner. Интеграции реализуются через JDBC, SDK и приложения Spring; email — через listeners и почтовую интеграцию. | Требует больше интеграционного кода и настройки уведомлений и мониторинга. SCDF больше не поддерживается поставщиком как open-source проект; будущие релизы доступны в коммерческом предложении. Выбор мог бы быть оправдан существующими Spring-приложениями или обязательством использовать коммерческий SCDF, но такие основания не установлены. |
| Apache Airflow + Spring Batch         | Airflow управляет общим пайплайном и внешними интеграциями, Spring Batch — обработкой чанками и восстановлением внутри job. В облаке Airflow может запускать контейнеризированные Batch jobs через `KubernetesPodOperator`.                                                                                                                | Добавляет второй фреймворк, согласование жизненных циклов, политик retry и видимости выполнения. Необходимость возможностей Spring Batch пока не установлена. Альтернативу можно пересмотреть при обоснованной потребности в восстановлении на уровне чанков или использовании существующих Batch jobs.                                             |
